# 설비 센서 신호 진단

이 스킬의 일은 **판단**이다. 세고 계산하는 일은 이미 `sf-signals` 가 했다.

평균·표준편차·추세·연속 초과 횟수를 다시 계산하지 마라. `signals/` 의 CSV 를 열어
직접 세지 마라. 숫자는 확정된 사실로 받고, 그 위에서 **"그래서 무엇을 할 것인가"** 만 판단한다.

## 0. 사실을 받는다

커맨드가 이미 `sf-signals` 와 `sf-actuate list` 출력을 붙여 놓았다. 없으면 직접 부른다:

```bash
# ${CLAUDE_PLUGIN_ROOT} 는 플러그인으로 설치했을 때만 설정된다.
_SF="${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/skills/diagnose/..}/bin/sf-signals"
[ -x "$_SF" ] || _SF="$(command -v sf-signals)"
"$_SF" <플랜트 경로> || echo "SF_SIGNALS: 없음 — 설치가 깨졌다"
```

**스크립트를 못 찾으면 네가 직접 CSV 를 읽어 계산하지 마라.** 설치가 깨졌다고 알린다.

확인할 것:
- 첫 줄 `SF_SIGNALS_PROTO: 1` — 프로토콜이 다르면 이 절차서와 맞지 않는 출력이다
- 마지막 줄 `SF_SIGNALS_OK` — 없으면 스크립트가 중간에 죽은 것이다. 숫자를 믿지 말고 알린다
- `ERROR:` 로 시작하면 여기서 멈춘다

키의 뜻 (전부 `WINDOW_MIN` 분 창 안의 값이다):

| 키 | 뜻 |
|---|---|
| `STATUS` | **마지막 샘플**이 한계 대비 어디 있나. OK / WARN / CRIT / NO_DATA |
| `OVER_WARN`, `OVER_CRIT` | 창 안에서 한계를 넘은 샘플 **개수** |
| `WARN_STREAK`, `CRIT_STREAK` | 마지막 샘플부터 거슬러 **연속으로** 넘은 개수 |
| `TREND_PER_HOUR` | 최소제곱 기울기. 시간당 변화량 |
| `MIN_TO_WARN` | 이 추세가 이어지면 주의 한계까지 몇 분. `0` = 이미 넘음, `none` = 24시간 안엔 안 닿음 |
| `FLATLINE` | 마지막 `flat_n` 샘플이 완전히 같은 값 (1 이면 센서 고착 의심) |
| `STALE_MIN` | 설비의 마지막 샘플이 몇 분 전인가 |
| `MISSING_SENSORS` | 설비는 살아 있는데 데이터가 없는 센서 |
| `DAYS_SINCE_MAINT`, `OPEN_WORK_ORDERS` | 정비 이력, 이미 열린 작업지시 수 |

## 1. 데이터를 믿을 수 있는가 (판단 1) — 이것부터

설비 문제와 센서 문제를 먼저 가른다. 센서가 고장난 걸 설비 고장으로 보고하면 멀쩡한 설비를 세운다.

```
STALE_EQUIPMENT 에 있다 (STALE_MIN ≥ stale_min)
   → 그 설비는 상태 판단을 **보류**한다. "정상"이라고도 하지 마라 — 모르는 것이다.
     조치: 수집 계통(센서 전원·게이트웨이·네트워크) 확인 요청. 창 안의 옛 값으로 판단하지 않는다.

FLATLINE: 1
   → 그 센서 값으로 판단하지 않는다. 살아 있는 센서는 소수점이 흔들린다.
     조치: 센서·배선 점검 요청. 다른 센서가 있으면 그것으로 설비 상태를 본다.

MISSING_SENSORS 에 있다
   → 알리기만 한다. 없는 센서로는 판단할 수 없다는 것을 명시한다.

한 설비에서 여러 센서가 **같은 방향으로** 이상하면 센서 문제가 아니라 설비 문제다.
한 센서만 튀고 나머지가 조용하면 센서 문제를 먼저 의심한다.
```

## 2. 지금 세워야 하는가 (판단 2)

정지는 되돌릴 수 없다. 가공 중인 제품은 폐기되고 재가동에 수십 분이 든다.
그래서 **한 샘플로 세우지 않는다.**

```
CRIT_STREAK ≥ 3
   → 즉시 정지 권고. 같은 설비의 다른 센서가 WARN 이상이면 확신을 높여 말한다.
     (예: 진동 CRIT 연속 + 온도 WARN 상승 = 베어링·윤활 계통 추정)

CRIT_STREAK 1~2
   → 아직 세우지 않는다. 현장 육안 확인 + 5분 뒤 재실행을 권고한다.

OVER_CRIT ≥ 1 이고 CRIT_STREAK = 0
   → 일시 스파이크다. 정지 아님. "재확인" 항목에 넣는다.
     같은 스파이크가 반복되면(다음 실행에서 OVER_CRIT 증가) 그때 점검을 예약한다.
```

정지를 권고할 때는 **운영자가 칠 명령을 그대로 적어 준다.** 네가 실행하지 않는다.

```
sf-actuate stop CNC-02 --reason "진동 8.45 mm/s (crit 7.1) 연속 12샘플, 온도 76 C (warn 70) 동반 상승"
```

## 3. 점검을 예약해야 하는가 (판단 3)

```
STATUS: WARN 이고 WARN_STREAK ≥ 3          → 다음 교대 점검 예약
MIN_TO_WARN ≤ 240 (4시간) 이고 추세 양수    → "이 추세면 N분 뒤 주의 한계" 라고 쓰고 점검 예약
DAYS_SINCE_MAINT ≥ 30 이고 위 둘 중 하나   → 예방 정비를 우선순위로 올린다
OPEN_WORK_ORDERS ≥ 1                       → 새로 발행하지 않는다. 기존 작업지시를 언급하고,
                                             내용이 이번 이상과 다르면 항목 추가를 제안한다
```

`MIN_TO_WARN` 은 직선 외삽이다. "예측"이 아니라 "이 속도면" 이다. 그렇게 말한다.

작업지시 발행은 되돌릴 수 있다(`sf-actuate cancel`). 그래서 **사용자가 승인하면** 네가 실행해도 된다:

```bash
sf-actuate --plant <경로> schedule-maintenance CNC-01 --when next-shift --reason "온도 +4.05 C/h, 61분 뒤 warn 도달. 정비 45일 경과"
```

`--reason` 에는 **센서·값·한계·추세** 를 넣는다. 6개월 뒤 "왜 예약했지?"에 답할 수 있어야 한다.
승인 전에는 명령을 보여주기만 한다.

## 4. 원인은 '추정'으로만 말한다

센서 조합은 원인을 **가리킬** 뿐 확정하지 않는다. 반드시 "추정"이라 쓰고 근거 센서를 붙인다.

| 조합 | 추정 | 아님 |
|---|---|---|
| 진동↑ + 온도↑ (같은 설비) | 베어링·윤활 계통 | "베어링 파손" (확정 어조) |
| 전류↑ 단독, 진동 조용 | 부하 증가·공구 마모 | |
| 압력↓ + 온도↑ (유압) | 누유·펌프 효율 저하 | |
| 한 센서만 튐, 나머지 조용 | 센서·배선 | 설비 고장 |

데이터에 없는 것(소음, 냄새, 작업자 보고)을 지어내지 마라.

## 5. 보고

이것만 보고한다. 스크립트 출력을 다시 붙여넣지 마라.

```
즉시 조치:   (있으면) 설비 — 권고 — 근거 (센서 값 / 한계 / 연속 횟수) — 운영자가 칠 명령
예약 조치:   (있으면) 설비 — 언제 — 근거 — 기존 작업지시 여부
재확인:      (있으면) 일시 스파이크, CRIT 1~2회 — 언제 다시 볼지
데이터 문제: (있으면) 센서 고착·끊김·누락 — 판단을 보류한 설비
정상:        설비 이름만 나열
```

없는 항목은 줄을 아예 빼라. 정상 설비에 대해 설명하지 마라 — 이름이면 충분하다.
근거의 숫자는 STATUS 라인에 있는 값을 **그대로** 옮긴다. 반올림도 하지 마라.

## 하지 말 것

- **설비 정지를 직접 실행하기.** 명령을 적어 주고 사람이 실행한다. (훅이 막지만, 훅에 기대지 마라)
- 스크립트가 준 숫자를 다시 계산하거나 `signals/*.csv` 를 열어 세기
- **한계값(`config/thresholds.csv`)을 고치기.** 경보를 없애는 가장 쉬운 방법이라 유혹이 있다.
  기준이 이상하다고 판단되면 그렇게 보고만 한다
- 원인을 확정 어조로 말하기 ("베어링이 파손됐습니다")
- 데이터가 끊긴 설비를 "정상"으로 분류하기
- 이미 작업지시가 열려 있는 설비에 같은 작업지시를 또 발행하기
- 사용자가 재촉한다고 판단 1(데이터 신뢰)을 건너뛰기
