# 2단계: 분석

이 스킬의 일은 **소견**이다. 세고 계산하는 일은 `sf-signals` 가 했고,
"그래서 무엇을 할 것인가"는 `decide` 가 한다. 여기서는 **설비가 어떤 상태인지**만 말한다.

평균·표준편차·추세·연속 초과 횟수를 다시 계산하지 마라. `signals/` 의 CSV 를 열어 직접 세지 마라.

## 0. 사실을 받는다

커맨드가 이미 `sf-signals` 출력을 붙여 놓았다. 없으면 직접 부른다:

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/sf-signals" <플랜트 경로>    # 경로를 생략하면 /tmp/sf-demo
```

**스크립트를 못 찾으면 네가 직접 CSV 를 읽어 계산하지 마라.** 설치가 깨졌다고 알린다.

확인할 것: 첫 줄 `SF_SIGNALS_PROTO: 1`, 마지막 줄 `SF_SIGNALS_OK`. `ERROR:` 면 멈춘다.

키의 뜻 (전부 `WINDOW_MIN` 분 창 안의 값이다):

| 키 | 뜻 |
|---|---|
| `NOW`, `NOW_SOURCE` | 기준 시각. `state.json` 이면 가상 시계다 |
| `STATUS` | **마지막 샘플**이 한계 대비 어디 있나. OK / WARN / CRIT / NO_DATA |
| `OVER_WARN`, `OVER_CRIT` | 창 안에서 한계를 넘은 샘플 **개수** |
| `WARN_STREAK`, `CRIT_STREAK` | 마지막 샘플부터 거슬러 **연속으로** 넘은 개수 |
| `TREND_PER_HOUR` | 최소제곱 기울기. 시간당 변화량 |
| `MIN_TO_WARN` | 이 추세가 이어지면 주의 한계까지 몇 분. `0` = 이미 넘음, `none` = 24시간 안엔 안 닿음 |
| `FLATLINE` | 마지막 `flat_n` 샘플이 완전히 같은 값 (1 이면 센서 고착 의심) |
| `STALE_MIN` | 설비의 마지막 샘플이 몇 분 전인가 |
| `MISSING_SENSORS` | 설비는 살아 있는데 데이터가 없는 센서 |
| `STATE` | running / stopped, speed. **정지한 설비는 값이 낮은 게 정상이다** |
| `DAYS_SINCE_MAINT`, `OPEN_WORK_ORDERS`, `PENDING_DECISIONS` | 정비 이력, 열린 작업지시, 사람이 아직 결정 안 한 제안 |

## 1. 데이터를 믿을 수 있는가 — 이것부터

설비 문제와 센서 문제를 먼저 가른다. 센서가 고장난 걸 설비 고장으로 보고하면 멀쩡한 설비를 세운다.

```
STALE_EQUIPMENT 에 있다 (STALE_MIN ≥ stale_min)
   → 소견: **판단보류**. "정상"이라고도 하지 마라 — 모르는 것이다.
     창 안의 옛 값으로 판단하지 않는다. 데이터 문제로 "수집 계통 점검"을 쓴다.

FLATLINE: 1
   → 그 센서 값으로 판단하지 않는다. 살아 있는 센서는 소수점이 흔들린다. 데이터 문제로 쓴다.
     다른 센서가 있으면 그것으로 설비 상태를 본다.

MISSING_SENSORS 에 있다
   → 데이터 문제로 쓴다. 없는 센서로는 판단할 수 없다는 것을 명시한다.

STATE 가 stopped
   → 소견: **정지중**. 낮은 값을 이상으로 읽지 않는다. 마지막 정지 사유는 decide 가 본다.

한 설비에서 여러 센서가 **같은 방향으로** 이상하면 센서 문제가 아니라 설비 문제다.
한 센서만 튀고 나머지가 조용하면 센서 문제를 먼저 의심한다.
```

## 2. 설비 상태 소견

신뢰할 수 있는 센서만으로 설비마다 하나를 고른다.

| 소견 | 기준 |
|---|---|
| **위험** | `CRIT_STREAK ≥ 3`. 다른 센서도 WARN 이상이면 "확신 높음" |
| **주의** | `STATUS: WARN` 이고 `WARN_STREAK ≥ 3`, 또는 `MIN_TO_WARN ≤ 240` 이고 추세 양수 |
| **재확인** | `OVER_CRIT ≥ 1` 인데 `CRIT_STREAK = 0` (일시 스파이크), 또는 `CRIT_STREAK 1~2` |
| **정상** | 위 어디에도 안 걸리고 데이터를 믿을 수 있다 |
| **판단보류** | STALE, 또는 믿을 센서가 하나도 없다 |
| **정지중** | `STATE: stopped` |

`MIN_TO_WARN` 은 직선 외삽이다. "예측"이 아니라 "이 속도면"이다. 그렇게 쓴다.

## 3. 원인은 '추정'으로만 말한다

| 조합 | 추정 | 아님 |
|---|---|---|
| 진동↑ + 온도↑ (같은 설비) | 베어링·윤활 계통 | "베어링 파손" (확정 어조) |
| 전류↑ 단독, 진동 조용 | 부하 증가·공구 마모 | |
| 압력↓ + 온도↑ (유압) | 누유·펌프 효율 저하 | |
| 한 센서만 튐, 나머지 조용 | 센서·배선 | 설비 고장 |

반드시 "추정"이라 쓰고 근거 센서를 붙인다. 데이터에 없는 것(소음, 냄새, 작업자 보고)을 지어내지 마라.

## 4. 소견서를 쓴다

`<플랜트 경로>/reports/analysis.md` 에 **덮어쓴다** (Write 도구). `decide` 단계가 이 파일을 읽는다.
형식을 지켜라 — 사람이 아니라 다음 단계가 읽는 문서다.

```markdown
# 분석 소견
CLOCK: <NOW 값>
WINDOW_MIN: <WINDOW_MIN 값>

| 설비 | 소견 | 근거 (STATUS 라인의 값 그대로) | 추정 원인 | 데이터 신뢰 |
|---|---|---|---|---|
| CNC-02 | 위험 (확신 높음) | vibration 8.45 (crit 7.1) CRIT_STREAK 12, temperature 76.11 (warn 70) WARN_STREAK 14 | 베어링·윤활 계통 (추정) | 양호 |
| CNC-01 | 주의 | temperature 65.86, +4.05/h, MIN_TO_WARN 61 · current OVER_CRIT 1 CRIT_STREAK 0 (재확인) | — | 양호 |
| PRESS-01 | 정상 (압력 제외) | temperature 47.98 (warn 60) | — | pressure FLATLINE, cycle_time MISSING |
| CONV-01 | 판단보류 | STALE_MIN 45 | — | 수집 끊김 |

## 데이터 문제
- PRESS-01.pressure: FLATLINE — 센서·배선 점검 필요
- PRESS-01.cycle_time: MISSING
- CONV-01: STALE_MIN 45 — 수집 계통 점검 필요
```

근거의 숫자는 STATUS 라인의 값을 **그대로** 옮긴다. 반올림도 하지 마라.

## 5. 보고

소견서 표를 그대로 보여 주고 한 줄 덧붙인다: `소견서: reports/analysis.md — 다음 단계: decide`.
`/sf-harness:run` 안에서 실행 중이면 보고하지 말고 파일만 쓰고 `decide` 로 넘어간다.

## 하지 말 것

- **조치를 제안하거나 실행하기.** "정지 권고", "점검 예약" 은 `decide` 의 일이다. 여기서는 상태만
- 스크립트가 준 숫자를 다시 계산하거나 `signals/*.csv` 를 열어 세기
- **한계값(`config/thresholds.csv`)을 고치기.** 경보를 없애는 가장 쉬운 방법이라 유혹이 있다.
  기준이 이상하다고 판단되면 그렇게 보고만 한다
- 원인을 확정 어조로 말하기
- 데이터가 끊긴 설비를 "정상"으로 분류하기
- 정지한 설비의 낮은 값을 이상으로 보고하기
