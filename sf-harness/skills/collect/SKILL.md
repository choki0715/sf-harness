# 1단계: 수집

이 스킬의 일은 **수집이 온전했는지 판단**하는 것이다. 값을 받는 일은 `sf-collect` 가 했다.

실제 공장에서는 PLC·게이트웨이가 이 일을 한다. 실습에서는 가상 플랜트가 시계를 N분 돌리며
값을 만든다. 어느 쪽이든 **에이전트가 센서 값을 만들거나 고치는 일은 없다.**

## 0. 사실을 받는다

커맨드가 이미 `sf-collect` 출력을 붙여 놓았다. 없으면 직접 부른다 (`${CLAUDE_PLUGIN_ROOT}` 는 플러그인 루트다):

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/sf-collect" <플랜트 경로> --minutes 5    # 경로를 생략하면 /tmp/sf-demo
```

확인할 것:
- 첫 줄 `SF_COLLECT_PROTO: 1`, 마지막 줄 `SF_COLLECT_OK`. 없으면 스크립트가 죽은 것이다 — 시계가 돌았는지 알 수 없으니 알린다
- `ERROR:` 면 여기서 멈춘다. `state.json 이 없다` 는 가상 플랜트가 아니라는 뜻이다 (`sf-demo-data` 로 만든다)

| 키 | 뜻 |
|---|---|
| `CLOCK_BEFORE` / `CLOCK_AFTER` | 가상 시계. 수집한 구간이다 |
| `<설비>.NEW_SAMPLES` | 이번에 받은 샘플 수 |
| `<설비>.SENSORS_SILENT` | 한계값에는 있는데 이번 수집에 값이 없는 센서 |
| `<설비>.STATE` | running / stopped, speed. 정지한 설비의 값이 0 에 가까운 것은 정상이다 |
| `SILENT_EQUIPMENT` | 샘플이 하나도 없는 설비 |

## 1. 수집이 온전한가 (판단)

```
SILENT_EQUIPMENT 에 있다
   → 이 설비는 이번 구간의 데이터가 없다. 분석 단계에서 STALE 로 나올 것이다.
     조치: 수집 계통(센서 전원·게이트웨이·네트워크) 확인을 **알린다**. 값을 채워 넣지 않는다.

SENSORS_SILENT 가 none 이 아니다 (설비는 살아 있는데 일부 센서만 없다)
   → 알린다. 그 센서는 분석에서 MISSING 으로 나온다.
     이전 수집에도 없었다면 "계속 없다"고 쓴다 — 새 문제인지 알려진 문제인지가 중요하다.

STATE 가 stopped 인 설비의 NEW_SAMPLES 가 0 이 아니고 값이 낮다
   → 정상이다. 정지한 설비는 진동·전류가 0 에 가깝다. 이상으로 보고하지 않는다.
```

## 2. 보고

```
수집:        CLOCK_BEFORE → CLOCK_AFTER, 총 N 샘플
수집 문제:   (있으면) 조용한 설비·센서 — 새 문제인지 계속인지
다음 단계:   analyze
```

없는 항목은 줄을 뺀다. `/sf-harness:run` 안에서 실행 중이면 이 보고를 따로 하지 말고 바로 `analyze` 로 넘어간다.

## 하지 말 것

- 조용한 설비의 값을 **추정해서 채우기**. 없는 데이터는 없는 것이다
- `signals/*.csv` 를 직접 쓰거나 고치기 (훅이 막지만, 훅에 기대지 마라)
- 수집 결과만 보고 설비 상태를 판단하기. "CNC-02 가 위험하다"는 분석 단계의 일이다
- 샘플 수를 다시 세기
